# README 컴포넌트 규칙

## 정보 계층

H1은 프로젝트 이름 하나로 쓴다. H2는 예시·설치·사용·파일 구성·실행 환경·라이선스처럼 독립된 주제에, H3는 도구나 설치 방식 구분에 사용한다. 실제 내용이 없으면 절을 생략한다. 기능 설명은 한 문장 소개 뒤에 필요한 만큼만 붙인다.

소제목 이모지는 예시 🎨, 설치 📦, 사용 ✍️, 파일 구성 🗂️, 실행 환경 ⚙️, 라이선스 📄처럼 의미에 맞게 고른다. 하위 설치 제목은 🛠️, 사용 예제는 💬처럼 역할을 반복해도 된다. 본문 문장이나 목록마다 이모지를 붙이지 않는다.

모든 소제목 글씨는 GitHub 기본 제목 색상을 사용한다. 이모지 자체의 색, 브랜드 배지 색과 구분한다. README에서 임의 CSS·`style`·`font color`를 사용하거나 제목을 색칠한 이미지로 대체하지 않는다. 제목 크기와 여백은 Markdown 계층으로 통일한다.

## 배지와 로고

상단에는 지원 도구·출력 형식 등 판단에 필요한 배지를 보통 2~4개 둔다. 배지를 늘리려고 다운로드 수, 빌드 성공, 라이선스를 추측하지 않는다. 같은 행에서는 `flat-square` 등 한 가지 스타일을 사용한다.

- 브랜드 배지는 공식 식별색을 참고하되 과도하게 다양한 색을 섞지 않는다.
- 일반 정보·외부 라이선스 배지는 한 가지 강조색을 쓴다. 예시 기준색은 파랑 `1864AB`다.
- 배지의 대체 텍스트에는 의미를 쓰고, 클릭하면 관련 절·원문·실제 상태 페이지로 이동하게 한다.
- 설치 대상 이름 앞에는 작은 로고 배지를 둘 수 있다. 이름은 이미지에만 넣지 말고 제목 텍스트로도 남긴다.
- Shields.io에서 `logo=`가 인식되지 않아도 이미지 요청은 성공할 수 있다. SVG의 로고 요소나 실제 렌더링을 확인한다. 빠진 로고를 정상이라고 보고하지 않는다.
- 로컬 SVG를 사용하면 출처와 라이선스를 확인하고 보존한다. 브랜드 로고를 임의로 그리거나 다른 제품의 로고를 해당 제품 고유 문양이라고 소개하지 않는다.

## 바로가기와 예시

바로가기는 실제 존재하는 절만 연결한다. 이모지나 이미지가 들어간 제목은 자동 생성 앵커에만 의존하지 말고 제목 위에 명시적 앵커를 둔다. 기존에 배포한 링크의 앵커는 제목을 수정해도 보존한다.

```markdown
[설치](#install) · [사용](#usage)

<a id="install"></a>

## 📦 설치
```

예시가 있으면 소개 뒤에 썸네일을 배치하고 클릭 시 원본 크기로 보게 한다. 대체 텍스트에는 이미지가 보여주는 결과를 설명한다. 실제 결과 캡처를 사용하고, 원본 파일·실행 예제로도 연결한다. 예시 이미지가 없으면 결과를 꾸며내지 말고 텍스트 사용 예제를 제시한다.

## 설치와 사용

지원 도구가 여러 개라면 도구별 H3로 나눈다. 개인 설치와 프로젝트 설치를 선택 가능한 방식으로 명확히 구분한다. 명령어는 언어가 지정된 코드 블록에 넣고 설명을 명령어 안에 섞지 않는다. 기존 명령어를 단순 윤문 과정에서 변경하지 않는다.

사용 예시는 실제 호출 방법과 결과를 받을 위치를 보여준다. 설치 설명을 사용 예시에 반복하지 않는다. 업데이트 방법은 짧은 TIP으로 분리할 수 있다.

## 표와 안내 상자

파일·용도, 구성요소·역할·라이선스처럼 비교할 정보는 2~3열 표로 만든다. 긴 문장이나 여러 줄 설치 명령은 표에 넣지 않는다. 표를 장식용 카드처럼 겹쳐 쓰지 않는다.

GitHub 안내 상자는 정보의 성격에 맞춰 제한적으로 쓴다. 업데이트 요령은 TIP, 실행 조건은 NOTE가 적합하다. WARNING은 실제 데이터 손실 등 주의가 필요한 동작에만 사용한다. 색을 넣기 위한 경고 문구는 만들지 않는다.

```markdown
> [!TIP]
> 이미 설치했다면 사용 중인 설치 경로에서 업데이트하세요.
```

## 라이선스

프로젝트 자체 라이선스는 실제 LICENSE 파일로 연결한다. 외부 의존성은 별도의 외부 라이선스 절에서 구성요소·용도·원문 링크를 표로 보여준다. MIT, SIL OFL 1.1 등 배지는 해당 구성요소 행 안에 넣어 적용 범위를 분명하게 한다. CDN으로 불러오는지 파일을 포함하는지도 실제 배포 방식에 맞게 설명한다.

표와 배지는 필요한 라이선스 원문·저작권 고지의 대체물이 아니다. 로컬에 포함한 외부 코드나 이미지의 기존 고지를 삭제하지 않는다. 라이선스가 확인되지 않으면 이름을 추측해 채우지 않는다.

## 검증 방법

GitHub Markdown API를 사용할 수 있으면 `gh api markdown --input <JSON 파일>`로 변환한다. JSON에는 `text`, `mode: "gfm"`을 넣고 저장소 맥락이 필요하면 `context`를 지정한다. 이 요청은 문서를 게시하지 않지만 내용을 GitHub에 전송하므로 비공개 자료는 전송 권한이 있을 때만 사용한다. 그 외에는 로컬 Markdown 렌더러를 사용한다.

변환 결과에서 제목, 표, 이미지, 안내 상자, 명시적 앵커 보존을 확인한다. 실제 화면 검증과 HTML 구조 검증을 구분해 보고한다. 공개 이미지 URL은 응답 상태와 콘텐츠를 함께 확인하고, 로컬 파일은 존재 여부와 경로의 대소문자를 점검한다. 최종 diff에서 코드 블록·고유명사·버전·라이선스가 의도치 않게 바뀌지 않았는지 확인한다.
